<objective>
Clear blocked placeholder tiles that earlier broken builds cached, without ever wiping the cache, and ship the offline instrument that proves the TESTER wire result. A blocked fetch caches a 6987-byte placeholder PNG and re-stamps a 7-day expiry on it, so an app that fixes its agent would keep showing blocked tiles for a week.

Purpose: POL-03 (ROADMAP Phase 28 success criterion 5, the purge bullet and the wire-level check's instrument), CONTEXT Runtime Decision "POL-03 cache purge amended" (binding): purge placeholder rows only, size AND md5, once per install and again when found, same approach as SecondBrain's contingency so the two do not conflict.
Output: `purgePlaceholderTiles` plus its trigger in `PlaceMapOsmdroidConfig.kt`, the real placeholder fixture, `PlaceMapTilePurgeTest`, trigger tests, and `tools/verify-osm-tile-cache.py` with its fixture test. No public API change.

Runtime decisions recorded by this plan (UNATTENDED run, source ai-auto, each reversible, all inside the locked Runtime Decisions):
- PD-1 [trigger]: the scan runs on the FIRST `configureOsmdroid` call of each process and also whenever the persisted install flag is unset. The flag key `placeholder_tiles_purged` lives in the hub's own prefs file (`yahirandroidtaste_osmdroid`) and is set only after a scan completed, so a scan that failed is retried on the next call. "Again whenever a placeholder is detected" can only mean "found by a scan" (osmdroid's downloader is internal and not hookable cheaply), so a per-process scan realizes it; `x-blocked` detection inside the downloader goes to the backlog, as CONTEXT allows.
- PD-2 [sync]: the scan is synchronous and best-effort. The `length(tile)` filter is answered from record headers, so it is cheap; the pure function stays synchronous for tests.
- PD-3 [return value]: `purgePlaceholderTiles` returns the deleted-row count, `0` for "nothing to do" (including a missing file) and `-1` when the scan could not run; only a non-negative result sets the flag.
- PD-4 [process flag]: a private `AtomicBoolean` marks the first scan of the process, evaluated BEFORE the install-flag test so a second call in the same process cannot rescan; `resetPlaceholderScanForTests()` is internal for tests (Pitfall 5).
- PD-5 [fixture]: the real placeholder bytes are fetched once with `curl` and committed as a test resource, so the pinned constants are proven against real bytes instead of trusted.

Flagged assumptions (the probe's `unclassified` POL-03 item, never silently dropped):
- FA-1: a per-process scan is an acceptable reading of "again whenever a placeholder is detected" (28-RESEARCH A3). Risk: the teamlead wanted strictly once per install.
- FA-2: SQLite `length(blob)` is answered from the record header, so the scan is cheap on a large cache (28-RESEARCH A4). Risk: a slow main-thread scan; mitigation if measured slow: move the call off-main without changing the pure function.
- FA-3: a second SQLite connection to `cache.db` is safe while osmdroid's `SqlTileWriter` holds its static connection (default busy handling); the whole call is wrapped so a lock error returns `-1`.
- FA-4: OSM may change the placeholder image; then the purge simply misses (fail-safe) and the plan-28-01 `Log.w` still fires.
