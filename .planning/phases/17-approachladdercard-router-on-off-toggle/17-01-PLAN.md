<edge_assumptions>
The spec-less edge probe left two items unresolved for VAPPR-04. Both are explicit planner assumptions, not silent drops:

1. Idempotency ("what if this runs twice on the same input?"): the card is stateless presentational chrome. The router value is hoisted by the caller, so recomposing with the same inputs renders identically and the card holds nothing that a second run could corrupt. The card does not de-duplicate emissions: a tap always calls onRouterChange with the tapped segment's value, and making that handler idempotent is the consumer's concern. No extra idempotency test is added beyond the emit tests. Dispositioned as T-17-09 (accept).
2. Concurrency ("if interrupted or run in parallel, what is guaranteed?"): the card owns no threads, I/O, or mutable shared state; composition and click callbacks run on the UI thread, so two quick taps emit two callbacks in order. Ordering and any cross-thread handling belong to the consumer's state holder. Dispositioned as T-17-09 (accept).
</edge_assumptions>
