# Phase 07 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase adds exactly one opt-in parameter pair (`TagChipUiModel.color`,
`AppChip`/`TagChipWithContextMenu`'s `containerColorOverride`) to two **existing** composables and
one auto-thread site (`CardTagRow`). No new composable, no new copy, no new spacing/typography
token. This contract therefore documents (a) the **precedence rule** that governs how the override
interacts with the two states that already exist (`isSelected`, `relatednessStrength`), and (b)
confirmation that everything else about chip anatomy is frozen. It intentionally does not invent
new visual language.

## Color

This is the load-bearing section for this phase: the precedence rule for the new override.

| Role | Value | Usage |
|------|-------|-------|
| Dominant / resting container | `MaterialTheme.colorScheme.surface` | `AppChip` unselected, no relatedness, **no override supplied** (`containerColorOverride == null`) — today's default, byte-identical |
| Secondary / selected container | `MaterialTheme.colorScheme.secondaryContainer` | `AppChip` when `isSelected == true` — **always wins over override**, unconditionally |
| Relatedness container | Computed by `relatednessVisual(relatednessStrength, colorScheme)` | `AppChip` when `!isSelected && relatednessStrength != null` — **always wins over override** |
| Override container ("accent" slot for this phase) | Caller-supplied `Color` via `containerColorOverride` | `AppChip` resting branch **only** — i.e. `!isSelected && relatednessStrength == null` (or relatedness not active). Rendered as-is: no contrast computation, no muting, no theme adjustment. |
| Content / label color | `MaterialTheme.colorScheme.onSurfaceVariant` (resting) / `onSecondaryContainer` (selected) / relatedness content color | **Untouched by this phase (D-01).** Do NOT add a new `contentColor` branch, do NOT "correct" the resting role to `onSurface`, do NOT wire `ColorUtils.contrastingForeground`. The consumer (SB) is contractually responsible for supplying an override color that stays legible against the existing `onSurfaceVariant` label in both light and dark theme. |
| Border stroke | `null` (selected) / relatedness border / `BorderStroke(1.dp, colorScheme.outline)` (resting default) | **Untouched by this phase.** A resting chip with a non-null override still draws its existing 1dp `outline` border — the override affects fill only, never the stroke. |
| Destructive | `MaterialTheme.colorScheme.error` | `TagChipWithContextMenu`'s "Delete tag everywhere" menu item/icon only — pre-existing, not touched by this phase |

**Precedence order (highest to lowest — this is the entire visual contract of this phase):**

1. `isSelected == true` → `secondaryContainer` / `onSecondaryContainer`, no border. Override is not
   even evaluated.
2. `!isSelected && relatednessStrength != null` → relatedness-computed container/content/border.
   Override is not evaluated.
3. `!isSelected && relatednessStrength == null && containerColorOverride != null` → override
   renders as the container fill; content color and border stay at their resting-default roles
   (`onSurfaceVariant` / 1dp `outline`).
4. `!isSelected && relatednessStrength == null && containerColorOverride == null` → today's
   resting default (`colorScheme.surface` / `onSurfaceVariant` / 1dp `outline`). Must be
   byte-identical to pre-phase rendering — this is the regression floor (ROADMAP success
   criterion 3).

**Accent reserved for:** the container fill of a resting (non-selected, non-relatedness-active)
`AppChip` or `TagChipWithContextMenu` **only**, and only when the caller explicitly supplies a
non-null `containerColorOverride`. Never applied to: the chip label/content color, the border
stroke, ripple/indication tint, `DropdownMenu` items, icon tint, or the "+N" overflow chip in
`CardTagRow` (it has no backing `TagChipUiModel`, so it always renders theme-default — see UI
Considerations).

**Hub/consumer boundary (do not blur):** the hub renders whatever `Color` it is given, unchanged.
It performs zero hash-from-name fallback, zero light/dark muting, zero contrast math. That policy
is SecondBrain's, computed app-side in a `@Composable` reading `isSystemInDarkTheme()`. Any attempt
by this phase's implementation to "help" by clamping/adjusting the supplied color breaks the
domain-free hub invariant and is out of scope.

## UI Considerations

Applicable state considerations resolved: 6 covered, 1 backstop, 1 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| override-vs-selected (combinatorial) | `AppChip`, `TagChipWithContextMenu` | ✅ covered | When `isSelected == true`, `containerColorOverride` is ignored — `secondaryContainer`/`onSecondaryContainer` render regardless of a supplied override (ROADMAP success criterion 4, asserted by test). |
| override-vs-relatedness (combinatorial) | `AppChip` | ✅ covered | When `relatednessStrength != null` and `!isSelected`, the relatedness-computed container/content/border win over `containerColorOverride` — the override is live only in the plain resting branch (ROADMAP success criterion 4). |
| override-null regression (default path) | `AppChip`, `TagChipWithContextMenu` | ✅ covered | `containerColorOverride == null` renders byte-identical to today's theme-role branch (`colorScheme.surface` / `onSurfaceVariant` / 1dp outline) — asserted by a parity test reusing `AppChipTest`'s idiom (ROADMAP success criterion 3). |
| zero-one-many (mixed-color row) | `CardTagRow` list-collection | ✅ covered | A row with mixed tags (some `tag.color != null`, some `null`) renders each chip independently from its own `tag.color` — no shared/row-level color state; adjacent chips may legitimately differ. |
| overflow chip has no model | `CardTagRow` "+N" chip | ✅ covered | The "+N" overflow `AppChip` has no backing `TagChipUiModel` and is never given a `containerColorOverride` — it always renders theme-default, per 07-CONTEXT.md's explicit note. |
| direct-call (non-auto-thread) sites | `AppChip`/`TagChipWithContextMenu` callers outside `CardTagRow` | ✅ covered | Raw non-tag `AppChip` uses (e.g. "Clear filter", language pill) pass `null` explicitly and stay theme-colored — confirmed in 07-CONTEXT.md's Specific Ideas. |
| long-text / label truncation | Chip label | N/A | Pre-existing `TextOverflow.Ellipsis` / `maxLines = 1` behavior is unaffected by container-fill color; not a new consideration for this phase. |
| which SB call sites route through `CardTagRow` vs. call chips directly | Consumer-side mapping | ⚠ unresolved | Explicitly out of this phase's boundary per 07-CONTEXT.md's Deferred Ideas — SB resolves this at its own plan time. The hub's only obligation is that both the auto-thread path (`CardTagRow`) and the explicit-param path (`TagChipWithContextMenu` direct callers) work correctly; which SB sites choose which is not this phase's concern. |
| pressed/ripple state over a custom container color | `AppChip` inner `Surface` (resting, override active) | 🧪 backstop | Default M3 ripple/indication continues to derive from `contentColor` (unchanged mechanism) — no test in this phase's plan pins ripple-tint legibility over an arbitrary caller-supplied fill. Treat as a held-out assumption: if SB reports a low-contrast ripple in dark theme against a light override color (or vice versa), that is SB's muted-color-policy responsibility (per the hub/consumer boundary above), not a hub defect. |
