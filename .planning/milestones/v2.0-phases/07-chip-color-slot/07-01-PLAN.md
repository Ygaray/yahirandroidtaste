<objective>
Add an opt-in, backward-compatible per-tag chip container-color override across the hub's tag-chip
stack (TAGCOLOR-01): `TagChipUiModel.color`, `AppChip`/`TagChipWithContextMenu`'s
`containerColorOverride`, auto-threaded at `CardTagRow`. The hub renders whatever `Color` it is
handed as-is — no contrast/muting computation, the consumer owns that policy (CONTEXT.md D-01); the
override loses to `isSelected`/an active `relatednessStrength`; every existing call site that omits
the new params keeps compiling and rendering byte-identical to today.

Purpose: unblocks SecondBrain's per-tag color feature (its own muted/theme-aware policy is computed
app-side) without the hub taking on any domain-specific color logic — the Phase 7 ROADMAP goal and
the v2.0 milestone's chip-color rider.

Output: four production files each gain one additive nullable parameter (or, for `TagChipUiModel`,
one additive nullable field); a new `CardTagRowTest.kt` and an extended `AppChipTest.kt` lock the
precedence order and the auto-thread wiring with real, deterministic tests; `api.txt` is
regenerated additively and the full governance battery (`testDebugUnitTest`, zero-baseline
`detekt`, both drift guards, `apiCheck`, `publishReleasePublicationToMavenLocal`) stays green.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Consumer app -> hub composable | A `Color` value crosses from caller code (SecondBrain/CalTracker, or this repo's own ExplorerActivity fixtures) into `AppChip.containerColorOverride` / `TagChipWithContextMenu.containerColorOverride` / `TagChipUiModel.color`, and is rendered as the chip's container fill with zero hub-side validation, clamping, or contrast computation (by design — CONTEXT.md D-01). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Tampering | AppChip.containerColorOverride / TagChipWithContextMenu.containerColorOverride / TagChipUiModel.color | low | accept | `Color` is a Kotlin inline value class wrapping a single packed numeric value (a `ULong` ARGB bit-pattern) — not a string, URI, or serialized blob — so there is no parse/injection surface a caller could exploit. The hub already accepts caller-supplied `Color` unvalidated today (`CardBase.accent`, `CardTypeChip.accent`); this phase extends the identical, already-accepted pattern to chips. Accepted as-is per D-01/UI-SPEC: the hub performing "helpful" validation/clamping would itself break the domain-free hub/consumer boundary this phase is contracted to preserve. |
| T-07-02 | Information Disclosure | same params | low | accept | A `Color` is a paint value with no capacity to carry PII or secrets, and the hub never logs, persists, or transmits it — it is read once per recomposition and drawn. No new disclosure surface versus any other `Color?` parameter already in this library. |
| T-07-03 | Denial of Service | same params | low | accept | `Color` is a fixed-size single-value inline class — an out-of-gamut or fully-transparent value at worst produces a legibility defect (explicitly the consumer's own muted/theme-aware policy responsibility per UI-SPEC's hub/consumer boundary), never unbounded allocation, recursion, or a crash. No resource-exhaustion vector exists. |
| T-07-04 | Spoofing / Repudiation / Elevation of Privilege | n/a | n/a | n/a | Not applicable — this phase crosses no identity, session, or privilege boundary; it is a same-process Compose parameter between library composables, with no auth/session context anywhere in the call chain. |
| T-07-SC | Tampering | npm/pip/cargo package installs | n/a | n/a | Not applicable this phase — no new external package or dependency is introduced; this is a pure additive Kotlin/Compose source change to four already-approved, already-imported files. The package-legitimacy gate has nothing to evaluate. |
</threat_model>
