# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Platform note:** This is a Jetpack Compose Android **design-system library**, not a web app.
The shadcn/web-oriented sections of the base template are marked "not applicable" below and
replaced with their Android/Compose equivalents. This phase adds **zero new visual/interaction
vocabulary** — WO-1 and WO-2 are internal component-shape unifications of two EXISTING, already-
shipped call sites (`FilterBar`→`ChipBar`, and the `TextCardBottomSheet`/`ListCardBottomSheet`
header+menu+rename block). **The locked design decision for this entire phase is: preserve every
existing pixel/dp value, color-role, typography-role, and copy string exactly as shipped today.**
This document's job is to pin down the two new/changed component **API and state shapes** so the
planner and executor implement one shape, not divergent ones — per the scope note in this agent's
brief.

## Spacing Scale

**Not a new scale — this section documents the exact dp values the two unify targets must
preserve**, sourced directly from the current shipped code (`FilterBar.kt`, `ChipBar.kt`,
`TextCardBottomSheet.kt`, `ListCardBottomSheet.kt`, all read in full this session).

| Token | Value | Usage (source) |
|-------|-------|-----------------|
| xxs (exception) | **2dp** | `FilterBar`'s `verticalArrangement = Arrangement.spacedBy(2.dp)` — the "tight gap between wrapped chip rows" convention. Must carry into `ChipBar`'s `expandable` mode exactly (see Component Contracts §WO-1). |
| xs | 4dp | Pin/Favorite icon `padding(top = 4.dp, end = 4.dp)`; `ImageCountIndicator`'s internal `HairlineSpacing` gap (unchanged, not touched this phase) |
| sm | 8dp | `ChipBar`'s bare-mode `horizontalArrangement`/`verticalArrangement` spacedBy(8.dp) (both axes); header `Row`'s `padding(vertical = 8.dp)`; `FilterBar`'s FlowRow `padding(vertical = 8.dp)`; post-categoryPath `Spacer(height = 8.dp)` |
| md | 16dp | Header `Row`'s `padding(horizontal = 16.dp)`; `FilterBar`'s FlowRow `padding(horizontal = 16.dp)`; `Button` (Edit note/Edit list) `padding(horizontal = 16.dp)`; categoryPath `Text` `padding(horizontal = 16.dp)` |
| lg | — | not used by either unify target |

**Exceptions:** the **2dp** tight vertical gap is an intentional, already-shipped exception to the
4/8/16 scale (not a new exception introduced by this phase) — it MUST be preserved verbatim inside
`ChipBar`'s new `expandable` mode; it must **not** leak into `ChipBar`'s existing bare mode
(`expandable == null`), which keeps its current 8dp `verticalArrangement` unchanged for all 5
existing SecondBrain call sites.

## Component API Contracts

This is the load-bearing section for this phase. It locks the two new/changed public surfaces so
planner and executor build one shape.

### WO-1 — `ChipBar`'s new `expandable` mode

**Locked signature** (extends today's `ChipBar`, every new param trailing + defaulted `null` so
all 5 existing SecondBrain call sites keep compiling unchanged):

```kotlin
data class ExpandableConfig(
    val expanded: Boolean,
    val onExpand: () -> Unit,
    val onCollapse: () -> Unit,
    val contentDescription: String = "Tag filters"
)

@Composable
fun <T> ChipBar(
    items: List<T>,
    key: (T) -> Any,
    itemContent: @Composable (T) -> Unit,
    modifier: Modifier = Modifier,
    testTag: String = "chip_bar",
    leadingContent: (@Composable () -> Unit)? = null,
    trailingContent: (@Composable () -> Unit)? = null,
    expandable: ExpandableConfig? = null,
    rawContent: (@Composable FlowRowScope.() -> Unit)? = null,
)
```

**State matrix (locked):**

| `expandable` | body-content mode | Visual/behavioral result |
|---|---|---|
| `null` | `items` (typed) | **Unchanged today's bare `ChipBar`.** Bare `FlowRow`, no `Surface`, `horizontalArrangement`/`verticalArrangement` both `spacedBy(8.dp)`, no `itemVerticalAlignment` override, no `maxLines` cap. Every existing SecondBrain call site (5 files) renders byte-identically to today. |
| non-null, `expanded = false` | `items` or `rawContent` | **New — collapsed chrome.** `Surface(fillMaxWidth(), tonalElevation = 1.dp, color = colorScheme.surface, Modifier.semantics { contentDescription = expandable.contentDescription })` wraps the `FlowRow`. Inner `FlowRow`: `fillMaxWidth().padding(horizontal = 16.dp, vertical = 8.dp)`, `horizontalArrangement = spacedBy(8.dp)`, `verticalArrangement = spacedBy(2.dp)` (the tight-gap exception — NOT the bare-mode 8dp), `itemVerticalAlignment = Alignment.CenterVertically`, `maxLines = 1`. Chevron `IconButton` (down arrow, a11y "Show all tags") composed as the **first** child inside the `FlowRow` content lambda, ahead of `leadingContent`. |
| non-null, `expanded = true` | `items` or `rawContent` | **New — expanded chrome.** Same `Surface`/`FlowRow` base as collapsed, plus: `maxLines = Int.MAX_VALUE`, and the `FlowRow`'s modifier additionally gets `.heightIn(max = (LocalConfiguration.current.screenHeightDp * 0.4f).dp).verticalScroll(rememberScrollState())`. Chevron shows the up arrow, a11y "Show fewer tags". |

**Composition order inside the `FlowRow` content lambda, whenever `expandable != null` (locked):**
1. Chevron `IconButton` (down/up `Icon`, `contentDescription = null` on the `Icon` itself — the
   a11y label lives on the `IconButton`)
2. `leadingContent?.invoke()` if non-null
3. Body content — **exactly one** of:
   - `items.forEach { item -> key(key(item)) { itemContent(item) } }` (typed mode), **or**
   - `rawContent?.invoke(this)` (freeform mode, carries `FilterBar`'s former callers)
4. `trailingContent?.invoke()` if non-null

`items` (typed) and `rawContent` (freeform) are **mutually exclusive alternate body-content
modes**, not combinable in one call — a caller migrating off `FilterBar` passes `items = emptyList()`
plus `rawContent = { ... }`; a caller using `ChipBar`'s existing typed shape leaves `rawContent =
null`. `testTag` continues to apply to the same `FlowRow` element (now optionally nested inside the
chrome `Surface`) in both modes, so any existing `testTag`-based UI-test lookup for `"chip_bar"` is
unaffected.

**Registry side (locked default, per D-02 "unify" fold-mechanism):** `FilterBar.kt` is **deleted
entirely** (no source-compat forwarding shim) — the audit's own wording is "retire `FilterBar` as a
standalone registered entry," and this is a hub-only breaking change already gated behind the
`v2.0.0` coordinated repin, so no shim is warranted. `ChipsFamilyScreen.kt`'s `FilterBar` `Entry`
block and its `FilterBarVariants()` demo function are removed; `ChipBarVariants()` gains a new
demo state exercising the `expandable` mode (collapsed + expanded) so the mode remains showcased in
the gallery. *(Overridable by planner if a staged-migration shim is judged necessary for
SecondBrain's 5 call sites — flagged here as the locked default, not a hard mandate.)*

### WO-2 — Shared sheet header + three-dot menu + rename dialog

**Extraction boundary (locked):** exactly the header `Row` (title + Pin/Favorite indicators +
`ImageCountIndicator` + three-dot `IconButton`), the three-dot `DropdownMenu` (Edit → Pin/Unpin →
Favorite/Unfavorite → Delete), and the rename `AlertDialog` block. The **categoryPath line stays
in each host sheet** — it sits between the header and `CardQuickView` today, is not part of either
Finding S-1's cited duplication, and (per the Color section above) the two sheets already render it
with a divergent color role that is explicitly out of this phase's scope to touch.

**Locked signature:**

```kotlin
@Composable
internal fun SheetHeaderMenu(
    title: String,
    isPinned: Boolean,
    isFavorite: Boolean,
    onTogglePin: () -> Unit,
    onToggleFavorite: () -> Unit,
    onDelete: () -> Unit,
    onDismiss: () -> Unit,
    onConfirmRename: (String) -> Unit,
    onEditRequest: (() -> Unit)? = null,
    imageCount: Int = 0,
    modifier: Modifier = Modifier,
)
```

**State matrix (locked, union of both sheets' current real call-site behavior):**

| Param | States | Result |
|---|---|---|
| `title` | blank / non-blank | `Text` only renders `if (title.isNotBlank())` — same guard as today in both files. (Not to be confused with `CardQuickView`'s own separate `title = ""` suppression trick further down each sheet — out of scope, untouched.) |
| `isPinned` | true / false | Pin icon (`Icons.Filled.PushPin`, `colorScheme.primary`, 16dp, `padding(top=4dp,end=4dp)`) shown only when true |
| `isFavorite` | true / false | Favorite icon (`Icons.Filled.Star`, `colorScheme.tertiary`, 16dp, same padding) shown only when true |
| `imageCount` | `0` (default) / `> 0` | `ImageCountIndicator(imageCount, ...)` is composed **unconditionally** in the shared header; it already no-ops (renders nothing, reserves no space) at `imageCount <= 0` — confirmed in `ImageCountIndicator.kt:41`. `TextCardBottomSheet`'s call site passes its real count; `ListCardBottomSheet`'s call site omits the param (defaults to `0`), reproducing List's current "no indicator" appearance exactly via the indicator's own existing no-op behavior — **not** a new conditional branch in the new composable. |
| `onEditRequest` | `null` / non-null | `null` → Edit row falls back to the local rename flow (`renameText = title; showRenameDialog = true`); non-null → Edit row calls `onEditRequest(); onDismiss()`. Both branches identical to both sheets' current code, now living inside the shared composable. |
| Delete tap | — | `onDelete(); onDismiss()` fires immediately — **no confirmation dialog**, matching today; do not add one |
| Rename confirm tap | — | `onConfirmRename(trimmed)` (only if non-empty after `.trim()`) → `showRenameDialog = false` → `onDismiss()` — exact existing call order, preserved |
| Rename cancel tap | — | `showRenameDialog = false` only — `onDismiss()` is **not** called (matches today) |

**Internal state (locked):** `showMenu`, `showRenameDialog`, and `renameText` (via
`remember(title) { mutableStateOf(title) }`, re-keyed on `title` exactly as today) move **into**
`SheetHeaderMenu` itself — they are no longer hoisted in each host sheet, since the whole block
that reads/writes them is being extracted.

**Region markers (locked, load-bearing):** the `// region:edit-menu-item` / `// endregion:edit-
menu-item` comment pair currently wrapping the Edit `DropdownMenuItem` in both files must move
**into** the new shared file, wrapping the same Edit item, verbatim. `TextListBottomSheetEditMenu
SourceContractTestSupport`-based test must be retargeted at the new file for these assertions (this
is an execution/test task, not a design decision — flagged here only because the markers are part
of this contract's required shape).

**Registry side (locked default):** `SheetHeaderMenu` is declared `internal` and added to
`ComponentRegistry.INTENTIONALLY_UNREGISTERED`, mirroring the existing `SwipeableActionRow`
precedent (`ComponentRegistry.kt:115-118`) — it is infrastructure extracted out of two already-
registered sheets, not an independently showcase-able visual archetype on its own (unlike
`CardQuickView`, which literally renders the visible card body and is independently registered).
Suggested allowlist reason string: *"Header/menu/rename chrome extracted from
`TextCardBottomSheet`/`ListCardBottomSheet` — infrastructure, not an independently showcase-able
archetype; already exercised indirectly via every sheet entry's own header/menu/rename
interaction."* Both `TextCardBottomSheet` and `ListCardBottomSheet`'s own registry `Entry`s in
`SheetsFamilyScreen.kt` are untouched — no demo/gallery changes needed for either host sheet.
*(Overridable: if the planner judges `SheetHeaderMenu` independently useful enough to warrant its
own gallery entry, registering it publicly — following the `CardQuickView` precedent instead — also
satisfies the registered-XOR-allowlisted invariant; either choice is contract-compliant, but pick
one and apply it consistently, not a mix.)*
