Go to the item, from snackbars and the outcome sheet

YAT v2.8.0 design options · 2026-10-17 · ui-designer for teamlead@vae-bilingual · design only, nothing is built until Yahir picks.

Fixed no action label: tap the snackbar itself Fixed Undo stays where it is today Fixed same go-to-item on the success sheet Fixed timeouts unchanged (4 s / 10 s) Fixed up to 3 visible, cascading Fixed swipe to dismiss

1 · Three visual directions (live, try them)

Each phone is interactive. Fire events with the buttons. Tap a snackbar body to go to its item (the screen switches to that card). Swipe it sideways to dismiss. Tap Undo to undo. A 4th event pushes the oldest out early (its Undo stays in the Undo Center). Timers are the real ones: 4 s for a plain notice, 10 s with Undo. They pause while your finger is on a snackbar.

A · Receipt card, cascading deck Recommended

The v2.7 Receipt look: a raised surfaceContainerHighest card with 16dp corners, a tone dot, the message and the item's name. Older snackbars tuck behind the newest one (scaled 94% / 88%). Tap the peeking edge to fan the deck out so every snackbar can be reached.

B · Refined inverse bar, stacked list

Closest to today: the Material inverse bar, now with 12dp corners and a 12dp side gap. All three show at once in a column, newest at the bottom near your thumb. Every snackbar can be tapped directly, but three of them cover about 190dp of the screen.

C · Floating pill, cascading

A compact, centered pill in the tone's container color, one line only. The lightest look, and it cascades like A. A single line truncates long German/Spanish messages, and the pill can't show the item's name on its own line.

The chevron is the only visual hint that a snackbar opens something. It isn't a text label. If you'd rather have none at all, every direction works without it; the tap and TalkBack behavior stay the same.

2 · The success / outcome sheet

The same go-to-item works on the success sheet, in both the Receipt and the Classic style (today Classic ignores the action slots). It uses no new button and no label: the receipt row that names the item becomes the tap target, with the same chevron. When a run changes several items, each batch row opens its own item. Undo and Undo all stay where they are.

3 · How a tap without a label stays accessible

A label-less snackbar is fine for TalkBack as long as the semantics carry what the visuals leave out. In Compose terms:

  • The body is one merged button. Modifier.semantics(mergeDescendants = true) plus clickable(role = Role.Button, onClickLabel = target.openLabel). TalkBack reads: "Created list Groceries. Button. Double-tap to open Groceries." The caller writes and localizes openLabel, the same way it does for every other YAT label.
  • It's announced when it appears. liveRegion = LiveRegionMode.Polite, so TalkBack users hear the message without hunting for it (what the Material snackbar does today).
  • Undo is still its own button. It stays a separate focusable child with its visible "Undo" text. It's also exposed as a customAction, so the TalkBack actions menu shows "Undo" and "Dismiss" while focus is on the body.
  • Swipe has an equivalent. TalkBack can't swipe a snackbar, so "Dismiss" is a custom action and dismiss { } semantics; Switch Access gets the same.
  • It stays up long enough. As today, each timeout passes through AccessibilityManager.calculateRecommendedTimeoutMillis with containsControls = true whenever the snackbar has Undo or a target, so TalkBack users get the longer system timeout. The 4 s / 10 s visual timings don't change.
  • The deck (A, C) is navigable. Older cards behind the front one stay in the semantics tree in order (newest first) with traversalIndex. TalkBack reaches all three without fanning the deck out.
  • 48dp touch target. Every snackbar row is at least 56dp tall, and the Undo button meets the 48dp minimum.
Snackbar [merged, Role.Button, liveRegion=Polite] text "Created list Groceries" onClick label "Open Groceries" ← FeedbackTarget.openLabel customActions ["Undo", "Dismiss"] └─ Button "Undo" ← stays a visible, focusable child

4 · API change (additive, v2.8.0)

Every change appends defaulted parameters or adds a new type. No existing call site changes, and the Metalava apiCheck diff is additions only.

// NEW: what a snackbar or sheet row points at. An opaque key, not a lambda (see the note below).
@Immutable
data class FeedbackTarget(
    val key: String,        // consumer-encoded, e.g. "card/LIST/42"; YAT never parses it
    val openLabel: String   // localized TalkBack click label, e.g. "Open Groceries"
)

// FeedbackEvent: one defaulted param appended to each item-bearing variant
data class Notify(message, duration = Short, val target: FeedbackTarget? = null)
data class WithUndo(message, undoAction, duration = Long, preview = null,
                    val target: FeedbackTarget? = null)

// NEW host: replaces a bare M3 SnackbarHost, shows up to 3 at once, swipe to dismiss
@Stable class FeedbackStackState(val maxVisible: Int = 3) {
    suspend fun show(event: FeedbackEvent): FeedbackResult   // Opened | Undone | Dismissed | TimedOut
}
@Composable fun rememberFeedbackStackState(maxVisible: Int = 3): FeedbackStackState
@Composable fun FeedbackStackHost(
    state: FeedbackStackState,
    onOpenTarget: (FeedbackTarget) -> Unit,      // the app navigates, e.g. routeForCard(...)
    modifier: Modifier = Modifier,
    style: FeedbackStackStyle = FeedbackStackStyle.Receipt   // the picked direction becomes the default
)
suspend fun FeedbackStackState.emitTrackedWithUndo(store: UndoHistoryStore, event: FeedbackEvent.WithUndo)

// Undo Center: rows can open their item too
UndoHistoryEntry(..., val target: FeedbackTarget? = null)        // internal ctor, copied from the event
UndoCenterScreen(..., onOpenTarget: ((FeedbackTarget) -> Unit)? = null)   // new overload, so trailing onClear stays last

// Outcome sheet: both styles
VoiceOutcomeUiState.Success(..., val target: FeedbackTarget? = null)
BatchRowResultUiModel(..., val target: FeedbackTarget? = null)
OutcomeSheet(..., onOpenTarget: ((FeedbackTarget) -> Unit)? = null)  // appended last to both overloads; neither ends in a trailing lambda

// Fixes a gap on the way: the snackbar's "Undo" is hard-coded English today (UndoTracking.kt)
FeedbackStackHost(..., undoLabel: String = "Undo", dismissLabel: String = "Dismiss")

Why a key and not an onOpen lambda? UndoHistoryStore is a Hilt @Singleton. A lambda that captures a NavController would leak the Activity into it, and Undo Center rows outlive the screen that made them. A string key is plain data. One app-level onOpenTarget maps it to a route, and that same handler can skip the navigation when the user is already on that item (SB survey gap G10). The existing SnackbarHostState.emitTrackedWithUndo and M3 hosts keep working unchanged; apps move to FeedbackStackHost when they adopt.

5 · Behavior rules

CaseRule
Tap the bodyCalls onOpenTarget(target), then dismisses that snackbar (result Opened). Without a target, a tap does nothing; it doesn't dismiss either.
Tap UndoSame as today (the store's one-shot guard). Afterwards the snackbar is no longer tappable, because its item may no longer exist.
Swipe left or rightDismisses that one snackbar (result Dismissed). It never undoes; Undo stays available in the Undo Center.
A 4th one arrivesThe oldest leaves early (result Dismissed). Nothing is lost: WithUndo entries live in the Undo Center.
TimersEach snackbar keeps its own timeout, as today (Short 4 s, Long 10 s, adjusted for accessibility). Proposed detail: the timer pauses while a finger is down on that snackbar or the deck is fanned out. Say no and it won't.
Deleted items (card, tag, clip)No target. The app passes null, because the item is in the Trash. A combined "Undo and open" is out of scope for v2.8.0.
After Undo allSheet rows and snackbars from that run lose their target (handled in the library once the entry is Undone).
Already on that itemThe app's onOpenTarget skips the navigation (G10). The library can't know the current route.
Inside a bottom sheetA sheet-local FeedbackStackHost works like today's SheetFeedbackHost, so tappable snackbars aren't hidden behind the sheet (G9).

6 · Recommendation

Direction A, the Receipt card with a cascading deck, plus the row-tap go-to-item on the sheet in both styles, and the chevron as the only hint that a snackbar can be tapped. A matches the v2.7 Receipt sheets you accepted, so snackbars and outcome sheets look like one system. It stays compact with three stacked (about 80dp), and its two-line layout keeps the item's name readable in long German or Spanish strings. B is the fallback if you'd rather keep the Material look and have direct taps over compactness.
